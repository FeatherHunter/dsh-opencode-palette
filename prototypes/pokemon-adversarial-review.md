## 结论摘要

**裁定：现方案的「暗场」成立，但成立的理由不是原方案给出的那条。** 原方案的理由是「审计的 `primary@background ≥ 3:1` 规则决定了亮黄不能当主色，所以只能做暗场」。本次评审**证伪了这条理由**：我造出了一套完整 37 个颜色、实跑仓库判尺 **38 硬性对 0 违例 / 15 UI 对 0 违例** 的浅色方案，并把最饱和的徽章黄 `#FFCB05` 放在**代码卡的金色标题带**上（`codeHeaderBg`，正文压 11.14:1）——徽章黄不但能在浅场活下来，还成了全场最大的品牌面。仓库自己的 12 套浅色预置里有 9 套正是这么干的（naruto 的 `#FFAFBE`、one-piece 的 `#95D2F9`、hello-kitty 的 `#F4B4D0` 饱和标题带压在近白代码卡上）。**所以 3:1 规则并没有规定「场」——它只规定「哪个槽位能放亮黄」；用审计规则倒推「必须暗场」是越权推理。**

**但暗场仍然更强，靠的是三条与审计无关的理由：**

1. **素材的场本来就是暗的**——委托书的前提写错了。01 号图鉴立绘不是「白卡纸 + 黑色画框」：它的**卡面本体**是 `#1C1C22`（58,800 px，21.60%）与 `#000000`（74,363 px，27.32%），页脚栏 `#0C0C10`（27,378 px，10.06%），全图墨色（L<0.02）占 **61.43%**；白色只有 38,229 px（14.05%），而且是画框四周 **30 px 的卡纸衬边**（第 y=24 行实测：`#1C1C22×70 #FFFFFF×420 #1C1C22×70`；第 x=280 列：`#FFFFFF×30 <画框> #FFFFFF×30`）。02 号的平涂蓝 `#799DFE` 占 55.91% 但 L\*=66，是**中调**不是浅场。真正浅场的只有 03 号，而它的场是**饱和金**。**全素材两个最大的色块是金 `#FEC901`（135,911 px = 16.35%）与暗卡族（160,541 px = 19.32%）**。现方案把 8 个表面槽直接排成卡面自己的明度阶梯（`#000000` 画框 → `#1C1C22` 卡面 → `#48484D` 头栏），是**翻译**；浅色方案是**重新推导**。
2. **「颜色必须来自图、不能想象」这条用户硬规则，只有暗场能以最严格形式兑现。** 素材的深色像素只落在 6 条窄色相带里（中性 / 青 H173 / 蓝 H207 / 绿 H108 / 金 H32.5 / 红 H357），明度窗口极窄；浅场要过 4.5:1 正文与 3:1 品牌位，只能靠**混色**把饱和中调压成深墨 ⇒ 我的浅色候选是 **17 直采 / 20 混色**，而现方案是 **37 直采 / 0 混色**。仓库自己的判尺允许三种来源（`docs/ip-presets-v3-notes.md:131-133` 直采/阶梯/混色，「第四种直接判负」），但宝可梦 v3.5 主动把自己收严到只许直采（`:161`「37 个颜色全部走这条路，**0 阶梯 / 0 混色 / 0 想象**」）。**换成浅场，这条判尺就守不住。**
3. **暗场的明度跑道是浅场的两倍。** 8 个表面槽的 L\* 跨度：现方案 **0 → 30.8**（最差相邻面对比 1.151），浅色候选 **84.0 → 100.0**（16.0，最差相邻 1.016）。浅场的层级只能靠发丝描边扛，暗场能靠「调」扛。

**代价要说清楚**：浅色候选并非劣作，它的判尺余量比现方案更宽（最紧一对 3.931 vs 现方案 3.24），语法核心 ΔE76 21.9 与现方案 22.0 持平，色相孤岛/角色碰撞/markdown 同值全 0；它还把仓库的质量标杆（kuromi，light）与 12 套浅色预置的house style（近白纸面 + 浅代码卡 + 深墨语法）学得很像。**但它拿不回「主色就是徽章黄」**——浅场的 `primary` 只能是 `#84633C`（107 px 的暗面金，饱和度 0.38），主按钮读起来是「古铜」而不是「皮卡丘黄」。

## 第 1 问：审计规则有没有越权

### 1.1 委托书的前提本身是错的（先纠事实，再谈规则）

委托书说「三张参考图是浅底（白图鉴卡 / 平涂蓝场 / 金场），只有 01 有黑色画窗，且那个黑是**白卡里的窗**」。逐像素核验后：

| 图 | 事实（来自 `adv3/structure.py`） | 结论 |
|---|---|---|
| 01 图鉴立绘 560×486 | `#000000` 74,363（27.32%）、`#1C1C22` 58,800（21.60%）、`#0C0C10` 27,378（10.06%）、`#FFFFFF` 38,229（14.05%）；明度普查：墨 61.43% / 浅 17.58% / 纸 15.61% / 中 4.22%；行/列扫描：白只出现在 30 px 卡纸衬边与 70 px 侧留白 | **黑是卡，不是窗**；白是衬边 |
| 02 wikiHow 平涂 | `#799DFE` 88,538 = 55.91%，L=0.3533 → L\*≈66；普查：中调 70.04% / 浅 25.21% | **中调场**，不是浅场 |
| 03「30」周年 | `#FEC901` 135,910 = 67.99%（占全素材 16.35%）；普查：浅 83.43% | 唯一浅场，**场的颜色是金** |
| 04 合志插画 | 无主场（`#FFFFFF` 2.91% / `#FEDE00` 2.54% / `#FB8603` 2.35%…）；中调 35.99% / 浅 36.32% / 暗 12.88% | 散点插画，不成场 |

**判读**：以「01 的负空间」定场这件事，方向其实是对的——但理由是 01 的**主体质量**（61% 墨）而不是「读了一张图的留白」。委托书之所以觉得暗场可疑，是因为把 01 误读成白卡；真实结构是**暗卡 + 白衬边 + 黄色方徽章**，现方案等于把卡面直接搬成了界面。

### 1.2 3:1 是不是「伪装成无障碍规则的美学规则」？——不是，但它被读了过宽

**它是真的无障碍规则。** `docs/theme-audit/criteria.md` §2.2 把 `borderActive` 与 6 个品牌位（primary/secondary/info/success/warning/error）对 `background` + `backgroundPanel` 的 3:1 列为硬性 UI 对；§2.3 规定任一硬性/UI 对不过就 `--check` 退出 1。这对应 WCAG 1.4.11（Non-text Contrast，UI 组件与图形对象 ≥3:1），不是审美偏好。

**但它的作用域被读错了。** 规则约束的是「**哪个槽位**能放亮黄」，不是「**场**必须暗」。理由有三条硬证据：

- `scripts/audit-themes.ts` PAIR_DEFS :119-147 的 3:1 集合里**没有任何一条是「背景 vs 页面」的对比要求**；被 3:1 卡住的是「品牌色 vs 页面」。所以「亮黄当主色」和「浅场」是两件可以拆开的事。
- 背景类槽位（`background`/`backgroundPanel`/`backgroundElement`/`sidebarBg`/`bubbleBg`/`inputBg`/`codeBlockBg`/`codeHeaderBg`）**不被要求与页面 ≥3:1**；它们只被 `text@表面`（4.5）与 `borderActive@表面`（3:1）约束。**浅色场里最饱和的黄色因此有一个合法且体量最大的落点：`codeHeaderBg`（代码卡的标题带）**。这就是我浅色候选里徽章黄的落点，`text@codeHeaderBg` = 11.14:1。
- 仓库自身的浅色预置证明这个装置是house style（`adv3/precedent.py` 输出）：

### 1.3 例外机制：哪些能备案，哪些不能

- `docs/theme-audit/exceptions.json` 只有 6 个字段：`notes` / `allowedCollisions` / `allowedMarkdownDuplicates` / `allowedBrandGeometry` / `allowedSyntaxRecede` / `allowedBackgroundIslands`。
- `criteria.md` §5 写明：**「例外只对第 4 节的设计 warning 生效，不能豁免第 2 节硬性对比度」**，并附「**新设计不得为了过审随手加例外**」。
- ⇒ **亮黄当主色这类对比度偏离，在本仓库里不可备案。** 现有 9 套记档主题（dc-comics / doraemon / dragon-ball / genshin / hello-kitty / marvel / transformers / star-wars / cyberpunk-2077）**没有任何一条备案涉及对比度**，全部只动设计 warning；cyberpunk-2077 甚至为几何记了 `allowedBrandGeometry:["unclassified"]`。
- ⇒ **仓库里也没有「浅场 + 亮主色」的先例**：12 套浅色预置的 primary 相对亮度只有 **0.047–0.162**，`primary@background` 落在 **4.45–9.01**（最低 doraemon 4.45，最高 genshin 9.01、zelda 8.98、hello-kitty 5.83、disney 5.78、mario 5.32、sailor-moon 5.09、one-piece 5.06、kuromi 4.83、lego 4.80）。**「浅场 ⇒ 主色必深」是本库的房规**，我的浅色候选是遵守它的（primary `#84633C`，5.27:1 / 5.18:1），不是破它的。
- ⇒ 另外：全库 60 套主题里 `primary@background` 的最低值是 mario-night 的 3.36；`#FFCB05` 对 10 套浅色预置各自的底色实测 1.24–1.52（disney 1.24 / doraemon 1.28 / genshin 1.27 / hello-kitty 1.52 / kuromi 1.32 / lego 1.31 / mario 1.44 / one-piece 1.34 / sailor-moon 1.36 / zelda 1.43）。**surface-map 的 1.14–1.52 数字是对的，错的是从它推出的「所以必须暗场」。**

### 1.4 本问小结

- **审计规则没有越权到「决定场」这一步，但它被当成了事后论证。** 真正卡住「亮黄当主色」的是 3:1 硬规则；真正卡住「亮黄当品牌面」的是**没人想过把黄色放进 `codeHeaderBg`**——仓库 9 套浅色预置早就在这么做。
- 规则的正确用法是：**「若要亮黄当主色，场必须暗；否则亮黄只能做牌/带，主色另请高明」**。现方案选了前者，我的候选选了后者，**两条都合规**。
- 所以「暗场 vs 浅场」不是审计问题，而是**素材问题**：素材的场（01 的 61% 墨）与明度跑道（暗 30.8 L\* vs 浅 16.0 L\*）以及「直采纯度」的可达性，才是真正的决定因素。

## 裁定

### 现方案的暗场成立，但理由要换

**最强的单一理由**：**只有暗场能让「37 个颜色全部是参考图里的真实像素」这条用户判准与「主色就是徽章黄」同时成立。** 素材的饱和色几乎全是中调（`#FFCB05` 亮度 0.66、`#799DFE` 0.353、`#FB8603` 0.26），浅场要 4.5:1 的正文与 3:1 的品牌位，就得把它们压成深墨——而深墨在素材里只有 6 条窄色相带、极窄的明度窗口（`#84633C` 107 px 一支金独扛 `primary`），于是直采率从 37/37 掉到 17/37。**用户说的是「所有颜色必须从提供的图中产生而来，不能自己想象」——混色仍然合规（仓库判尺允许，harry-potter 15/8/19、sailor-moon 8/10/19），但宝可梦 v3.5 主动把自己收严到「0 阶梯 0 混色 0 想象」，换成浅场，这条更严的判准就守不住了。** 叠加上「01 号卡面 61% 是墨、代码卡就是画框黑」与「暗场明度跑道 30.8 L\* vs 浅场 16.0」，暗场在这条判准下更强。

**次强理由（与审计无关）**：素材自己的场就是暗的（01 的墨色 61.43%；两个最大色块是金 16.35% 与暗卡 19.32%）。现方案把 8 个表面槽直接排成那张卡面的明度阶梯，是翻译而不是再创作。

### 顺带纠正的三处

1. **「浅色主题不能用亮黄」是错的**，应改为「浅色主题里亮黄不能当 `primary`；它可以当 `codeHeaderBg` 的金色标题带，而且仓库 9 套浅色预置已经在这么用」。
2. **「所有 7 套浅色预置」应为 12 套**，且它们的主色相对亮度只有 0.047–0.162、`primary@background` 4.45–9.01 —— **「浅场 ⇒ 主色必深」是本库房规，审计不是它的成因**。
3. **3:1 规则不可备案豁免**（`criteria.md` §5：例外只对第 4 节设计 warning 生效；现有 9 套记档主题无一涉及对比度），所以「深场」不是为了让亮黄过关而开的口子，**它只是恰好让亮黄可以合法地当主色**。

### 什么会改变我的结论

- **若 01 号图的卡面本体真的是白的**（委托书的前提成立），则暗场就变成「读一张图的留白」，而素材的场其实是浅的——那时浅场是翻译、暗场是再创作，**浅场赢**。我按像素核验后不认为前提成立（白色只有 30 px 衬边，墨色 61.43%），但如果有人能拿出 01 号图的高分原图证明卡面是白底，**这条理由立刻翻转**。
- **若用户明确说「徽章黄必须是主色」**（而不是「必须是品牌面」），则浅场无解——3:1 不可备案豁免——暗场成为唯一解。
- **若宿主 UI 在浅底上靠「调子」分层而不靠描边**（例如大面积相邻表面需要 ≥1.05:1 才不糊在一起），则我的候选最差相邻 1.016 会被判失败，浅场出局。
- **若允许在浅场里给 `primary` 破例**（改判尺、给 3:1 加例外条目），则浅场可以用 `#FFCB05` 当主色，直接消掉「古铜按钮」这个最大短板，**届时浅场与暗场至少平手**——但那需要改仓库判尺，不是主题设计能做的事。

## 结论摘要

1. **破 —— 「直采」判尺把 16/37 个颜色钉在了量化台阶上，而不是颜色上。**
   决定性判据是「自身感知邻域」：把某颜色字面命中的像素，连同同图内 ΔE76≤2 的全部像素算作它的邻域，看字面值占自己邻域多大比例。

### 2. 「exact pixel」是不是用户那句话的正确读法？

#### 2.1 用户原话与两种读法

> 「所有颜色必须从提供的图中产生而来，不能自己想象」

这句话的**约束对象是"想象"**，不是"派生"。

- 读法 A（作者采用）：每个颜色必须等于四张图里某个像素的**字面值**。
- 读法 B（更贴近原意）：每个颜色的**来源**必须落在四张图的像素上；来源可以是那个像素本身，也可以是从图上像素派生的明度台阶或固定比例混合——但不能凭空。

读法 B 就是仓库自己对其余 20 套 IP 的判尺：`notes:132`「**阶梯**：采样色的明度 / 彩度台阶」、`notes:133`「**混色**：两个采样色的固定比例」、`notes:147`「② 阶梯（采样色沿 OKLCH 明度轴取台阶，公式写在卡片上）；③ 混色（两个采样色按固定比例在 sRGB 空间混合）」。**派生色在仓库的定义里就是"从采样色来的"，而采样色来自图；所以派生色同样满足"从图中产生而来"。** 把阶梯/混色计进"想象"，是把"派生"和"捏造"混为一谈。

#### 2.2 证据权重被倒挂了

这是本节最关键的一击，因为它完全用仓库自己的文本：

| 仓库文本 | 事实 | 含义 |
|---|---|---|
| `notes:131`（哈利波特） | 「#CAA654 在 3.jpg 领带里找到 **13 个**精确像素，#0B223B 在 4.jpg 夜空找到 4272 个，**#91BEAE 在 4.jpg 邓布利多银须上找到 4 个**」 | 4 px 的字面巧合 = **合格** |
| `notes:251`（赛博朋克） | 「syntaxType #7A9E92、syntaxOperator #7876A5、syntaxKeyword #C3B50C 等**全库仅 1 px**，是为同时满足判尺与分离度而在语料里做约束搜索得到的解」 | 1 px = **合格**，但明说是"搜索出来的解" |
| `notes:161`（宝可梦） | 「37 个颜色全部走这条路」 | 全部 37 槽都要求字面命中 |

**判尺给"恰好撞上某个色值"的信用等级，高于"从 4,272 px 真实区域按公式反解"。** 这不是纪律，这是把证据权重接反了：
- 4 px 的 `#91BEAE`（银须上的一点）≈ 一个像素级巧合，取它的唯一理由是"它字面存在"。
- 宝可梦的 `sidebarBg #060606`（675 px 的 1px 竖线）≈ 一个近黑量化桶，取它的唯一理由也是"它字面存在"——**而它的邻域 95.8% 是 `#000000`**。

更要命的是**顺序**：赛博朋克是"先做判尺约束搜索、再吸附到字面像素"（`notes:251` 明说），宝可梦是"先定岗位、再去找像素"。后者在数学上必然产生 find-to-fit 产物——你要求 8 个背景槽排成一条冷调明度阶梯，而语料里根本没有一条现成的 8 级阶梯，于是每个槽位都只能去**最近的某个像素桶**上凑，凑出来的就是 1px 细线、17 连通块、53 连通块。

#### 2.3 实测：按仓库自己的宽松判尺重建最弱角色

用仓库的定义（直采 / 阶梯 / 混色）加上仓库自己的审计规则重解 37 槽，脚本 `adv1\alt3.py`（审计 harness）+ `adv1\alt4.py`（约束搜索，读 `adv1\intent.json` 的 OKLCH 意图约束表），产物 `adv1\alt_intent.json`。
**求解顺序刻意与赛博朋克一致：先做判尺约束搜索，再吸附到字面像素。**

对照结果（`adv1\final_analysis.txt:114-131`）：

| 指标 | CURRENT（0 阶梯 / 0 混色） | ALT（12 直采 / 11 阶梯 / 14 混色） | 判读 |
|---|---|---|---|
| 审计违例（全 37 槽，含跨组同值） | **1** | **0** | ALT 更好 |
| 37 槽两两最小 ΔE76 | **0.00** | **2.15** | ALT 更好 |
| ΔE76 < 3 的槽对 | **9** | **1** | ALT 更好 |
| ΔE76 < 5 的槽对 | **16** | **1** | ALT 更好 |
| 语法核心 5 色最小 ΔE76 | 21.96 | **32.38** | ALT 更好 |
| 8 个表面槽最小 ΔE76 | **1.65** | **5.04** | ALT 更好 |
| 8 表面 L\* 阶梯每步 ≥1.4（`notes:31` 自订标准） | 0/7 步不达标（min 1.65） | 0/7 步不达标（min 1.42） | 持平 |
| 出处构成 | 27 字面 / 10 派生 | 12 字面 / 25 派生 | — |

也就是说——**那 41% 里被当作"provenance 信用"的部分，本来就不是配色"像不像图"的主要来源；感知覆盖才是。** 用 20 个 1 px 细线换来的覆盖率，换不来任何感知收益。

ALT 相对 CURRENT 的关键改动（`adv1\alt_intent.json:41-198`，每条都带配方与锚点）：
`sidebarBg #060606 → #1E222C`（混色 #191917 × #4B76E7 90%）、`diffRemoved #FE4C1C → #CA5900`（阶梯 #FB8603 L 0.736→0.596）、`markdownBlockQuote #BDBDC3 → #B0AAAA`（阶梯 #A49E9E L 0.704→0.744）、`syntaxKeyword #C790A3 → #B96D98`（混色 #799DFE × #F93D32 50%）、`syntaxComment #85858A → #757574`（混色 #FFFFFF × #191917 40%）、`syntaxOperator #7A7A7F → #777789`（混色 #289BCA × #EE4027 60%）、`syntaxString #80CAAF → #558549`（阶梯 #4F7F43）、`syntaxType #658F8B → #5C9390`（阶梯 #3E7572）、`syntaxFunction #6E9BBC → #5890C4`（阶梯 #207BC2）、`markdownEmph #F9B584 → #FAB685`（**直采，4.jpg 真平色区 1,009 px**）、`text #EEEEF4 → #EEEEEE`、`textMuted #D3D3D8 → #D1D1D1`（阶梯 #FFFFFF L→0.86）、`diffAddedLineNumberBg #111312 → #011E1E`、`diffRemovedBg #0C0406 → #170001`、`diffRemovedLineNumberBg #060606 → #180604`（**与 sidebarBg 同值问题一并解决**）。

#### 2.4 结论

**读法 A（严格字面像素）在这个问题上是范畴错误。**
理由三条，按强度排序：
1. **它替换了设计判断，而不是加强它。** "这个颜色必须等于某个像素"回答的是"这个 hex 从哪来"，而"这个颜色该是什么颜色"才是设计问题。判尺只管前者，就把设计判断从流程里挤出去了。
2. **它把产出推向"岗位色落在无关碎片上"。** `notes:168` 写"keyword 皮卡丘嘴部藕粉"——嘴部的粉色渐变被派去当代码关键字；`notes:173` 写"diffRemoved 只有 16 px"——16 px 被派去当删除行标记。这正是任务描述里担心的那种退化，**而且已经在成品里发生了**。
3. **它的度量是自我实现的。** "0 阶梯 / 0 混色"是一个关于**方法计数**的指标，不是一个关于**证据质量**的指标。把"有多少个槽位用了三种方法"当严格度，等于用"我没用第二个工具"当"我把活干好了"。

### 3. 「0 阶梯 / 0 混色 / 0 想象」「迄今最严」是不是误导？

| **宝可梦 v3.5** | `notes:161` | **只有直采** | **27 / 0 / 0** | 是 | **是** |

- 「**0 想象**」不是宝可梦首创：海贼王（`notes:219`）明写「37 个颜色无一例外，**0 想象**」。
- 「**单一来源**」不是宝可梦首创：海贼王也是单一来源。
- 「**三种来源**」也不是宝可梦的独占：迪士尼 v4（`notes:31`）"5 张图实测像素 + 定比混合"更早就在用。
- 宝可梦真正独有的只有一条：**单一来源且必须是字面像素**。而这条独有规则的代价，本报告已用 16 个量化台阶和 6 个图注带颜色量化出来。
- 「**迄今最严**」在文档内部没有支撑：`notes:129` 哈利波特管自己那一版叫「**判尺（比 v3 更严）**」——"更严"是相对**它自己上一版**说的。同一篇文档里两处"最严"用的是不同的参照系（一个比上一版，一个比别的 IP），但从未给出跨 IP 的严格度排序依据。**要立"最严"，就得先说清"严"衡量的是什么；不说的"最严"是修辞。**

#### 3.2 37 色里哪些其实是"派生"而不是"采样"

按 1.2 的邻域判据：
- **17 槽是"采样"**（字面值 = 色区主体，share 51%–100%）。
- **4 槽是小台阶**（`border` / `syntaxOperator` / `textMuted` / `backgroundPanel`）。
- **16 槽实质是"派生"**——它们的字面值是某个更大色区的量化台阶（share 9.9%–43.6%）。其中最极端的两支：
  - `sidebarBg #060606`：邻域 77,658 px，95.8% 是 `#000000`。**sidebar 底色实际上就是 code block 底色，只是偏了 1.65 ΔE。**
  - `syntaxString #80CAAF`：邻域 6,779 px，61.4% 是 `#7FC9AE`——**而 `#7FC9AE` 就是 `diffAdded` 自己**。"字符串绿"与"新增行绿"在屏上是同一个颜色（ΔE 0.36），而仓库的碰撞判定只比精确同值（`audit-themes.ts:632-648`），所以这对撞色在审计里是隐形的。
- 再加两条"实质派生但被记成直采"的：
  - `bubbleBg #28282D` 所在区域的众数是 `#1C1C22`（29,400 px = `background` 本身，ΔE 5.86）——它其实是 background 的一档阶梯。
  - `backgroundPanel #37373B` 所在区域众数是 `#40404A`（= `backgroundElement`，ΔE 5.71）。

也就是说，作者**其实已经在用阶梯和混色**（`notes:163` 明写"8 个背景槽收进同一条冷调明度阶梯"），只是把"阶梯"这件事伪装成了"逐个直采"，好让"0 阶梯"这个计数好看。**这不是纪律，这是记账。**

#### 3.3 结论

「0 阶梯 / 0 混色 / 0 想象」作为**方法计数**是同物异名，作为**严格度宣称**是不成立的；而且它在**实质上不成立**（背景家族明明是阶梯，只是记成了直采）。"0 想象"这一条是唯一完全站得住的——37/37 命中。

#### 4.2 三条要害

1. **3.jpg 基本是空白的。** 这张图 67.99% 的像素是同一个黄 `#FEC901`（135,910 px = 全语料的 16.4%），**它不在 37 色里**；配色反而去 2.jpg 挑了同色族的邻居 `#FAE721` 当 markdownHeading。3.jpg 对整块配色的字面贡献只有 1,050 px（#FFFFFF 985 + #000000 31 + #060606 5 + #111312 1 + #FFCB05 28）。

3. **"41%" 这个数字要打折。** 它看起来像"四张图里 41% 的像素就是这 37 个色"，但其中最大的一块来自 01 号图那一行 19 px 的图注带 + 卡面黑白结构；把感知邻域口径打开（67.04%）反而说明：图里那些大色区**不是**字面等于配色本身，而是**恰好近**。也就是说，"取自图"在多数槽位上成立的方式，是"近到可以算"，不是"就是"。

#### 4.3 结论

- "37 色都真实出现在四张图里"：**成立**（0 想象）。
- "37 色就是这些图的配色"：**不成立**。3.jpg 贡献 0.53%；8 支颜色来自一行图注；16 支是量化台阶。

## 可操作的修法

> 按"改动量 / 收益"排序。每条都给了可执行的判据或取值。

### 修法 1（最高优先）：把"角色碰撞"从"精确同值"升级为"感知同色"，并把 bg 组纳入检查集

**问题**：`audit-themes.ts:501-506` 排除了所有 bg 组与四个 `diff*Bg` 槽位；`:632-648` 只比 `v.toLowerCase()` 精确同值。
**后果**：`sidebarBg #060606` 与 `diffRemovedLineNumberBg #060606` 字面同值（ΔE 0.00）从未被检查，而 `notes:169` 却宣称"0 角色碰撞"。
**改法**：
- 碰撞判据改为 **ΔE76 < 3**（或 CIEDE2000 < 2.5），并在报告里并列"字面同值"与"感知同值"两个计数。
- 检查集从 25 个 DESIGN_ROLES 扩到**全部 37 槽**（bg 组 + diff*Bg 全部纳入）。
- 立刻会暴露 9 对 ΔE<3：0.00（sidebarBg≡diffRemovedLineNumberBg）、0.36（diffAdded≡syntaxString）、1.65（codeBlockBg≡sidebarBg≡diffRemovedLineNumberBg）、2.40、2.67、2.89。**这一条改动的收益最大、成本最低。**

### 修法 2：加一条"区域主导度"硬判据，替掉"命中像素数 > 0"

现判据是"命中即合格"。建议改为：**一个颜色要算"直采"，必须满足 `px ≥ 300 且 interior ≥ 30%`，或 `cloud/px ≤ 2`**（两个条件至少一个成立，且字面值占自身 ΔE≤2 邻域 ≥ 50%）。
按此判据，现有 37 槽里 **16 槽立即判负**（清单见 §1.2 最后一列），包括作者自己已在 `notes:173` 备案的三支。
**这条判据的价值在于它同时定义"什么叫派生"**：只要一个色的出处是"某个大色区里的一个桶"，它就属于派生，应该走阶梯/混色并写配方，而不是冒充直采。

### 修法 3：把判尺口径改成仓库的统一口径（阶梯 / 混色 合法），但把"锚点"卡死

建议在 `notes:161` 处改写为：
> 判尺：每个颜色只允许三种来源——**直采**（hex 等于语料里某个像素，且该像素所在区域的众数色与它 ΔE76 ≤ 2）／**阶梯**（采样色沿 OKLCH 明度轴取台阶，公式写在台账卡片上）／**混色**（两个采样色按固定比例在 sRGB 空间混合）。**0 想象**（任何一档都必须有像素出处）。
> 与其它 IP 的差别不在来源种类，而在于**本套的锚点必须同时满足岗位分离度约束**（先做约束搜索，再吸附到字面像素——与赛博朋克 `notes:251` 同一顺序）。

这样"最严"就落在一个**可比较的维度**上（源头的区域主导度 + 分离度），而不是"我用了几种方法"。

## 结论摘要

### 一句话判词

**这套调色板是一份诚实的直采，但不是一份被设计过的调色板。** 37 个颜色全部是参考图里的精确像素命中（这一点经我逐位复算，确认成立），但其中 **10/37（27%）锚在少于 60 个精确像素上**，而**全部结构灰阶 —— 5 个颜色、包括作者自己声称的「8 级灰阶」—— 采样自 01 图鉴立绘同一条 18 像素高的抗锯齿边**。换句话说：作者以为是「冷场暖字」的 8 级灰阶，实际上是**一条 JPEG 模糊渐变被切成了不等距的 5 段**。

### 最致命的 6 件事（按可改性 × 影响排序）

1. **`textMuted` #D3D3D8 是全仓 23 套预置里最不 muted 的次要文字**（CR 11.37:1，排名 23/23；全仓中位 8.83:1；暗色 13 套中位 8.27:1）。它比正文只低 22.5%，而暗色预置中位是 45.9%。一个「次要标签」读在 11:1 上，不是次要，是正文。而它的出处只有 **41 px**，且 92.7% 落在 01 图 y=440–457 那条抗锯齿带里 —— 也就是说**它根本不是被选出来的，是从图上刮下来的一条边**。

#### 1.2 相邻槽位的感知步进（作者排定的顺序）

| 步进 | ΔL\* | 亮度倍数 | 对比比 CR | ΔE76 | ΔE00 | 判定 |
|---|---|---|---|---|---|---|
| background → backgroundPanel | +12.70 | ×3.24 | 1.43 | 12.82 | 8.66 | ✅ 清晰 |
| backgroundPanel → backgroundElement | **+4.23** | ×1.36 | **1.16** | 5.71 | **4.60** | ❌ 低于发丝线阈值 |
| backgroundElement → codeHeaderBg | **+3.32** | ×1.25 | **1.13** | 4.69 | **3.86** | ❌ 低于发丝线阈值 |
| codeHeaderBg → border | +6.71 | ×1.50 | 1.28 | 6.99 | 5.78 | ⚠️ 过线，但方向反了 |

**可见阈值模型**（本文采用）：大面积相邻面（面 vs 面）需 ΔL\* ≳ 2 才刚可辨、≳ 5 才可靠；1px / 0.5px 发丝线在暗底上需 **CR ≳ 1.30** 才看得见、≳ 1.50 才稳。

据此：**两级步进（1.16 / 1.13）在物理上低于「一条线」的可见度，却承担着「两级面」的语义**。用户会把 `backgroundPanel`、`backgroundElement`、`codeHeaderBg` 读成同一个面上的噪声，而不是三个层级。最大级差 / 最小级差 = 12.70 / 3.32 = **3.83:1** —— 一个被称为「阶梯」的东西，不该有 3.8 倍的不匀。

**彩度也不单调**：C\* 4.41 → 2.66 → **6.50** → 3.19 → 1.23。`backgroundElement` #40404A 的紫调是 `border` #58585A 的 **5.3 倍**，却是两者之间更暗的一个 —— 也就是说这个阶梯在色相方向上是**倒着走的**（冷的往冷里跳，灰的往灰里退）。

#### 1.3 根因：这套参考图里根本没有阶梯，只有三条带

把 830,418 px 语料里所有近中性（C\* ≤ 8）、**精确命中 ≥ 60 px**（即可用出处的）色全部列出，排序后只剩 22 个色，且它们聚成**三条带**：

| A 暗带 | 3.42 – 10.50 | #0C0C10 27,378px(01)、#140D0E 82、#111111 102(3/4)、#111115 72、#121212 91、#131313 81、#131317 79、#181816 69、**#191917 1,613px(4.jpg)**、#1A1A18 125、**#1C1C22 58,800px(01)** | 内部步距 0.50–1.77 ΔL\*，基本是**一个色调的十几个别名** |

#### 1.5 `border` #58585A 是不是故意比 `codeHeaderBg` 亮？

**是意外，不是设计。** 三条证据：

1. **出处无关**：#58585A 来自 4.jpg 插画阴影区（993 px，12.98% 填充），#48484D 来自 01 立绘底边（37 px，0.55% 填充）。两个颜色采自两张图、两种完全不同的图像结构，亮暗关系是两次独立采样决策的**副产品**。
2. **量级倒挂**：发丝线与它框住的带相差 +6.71 ΔL\*，**跨度比 3 个表面步进里的 2 个（4.23 / 3.32）都大**。换句话说：**一条 0.5px 的线，比两个面之间的层级差还响。**
3. **墨量失衡**：渲染实测 `border` 228,119 px，占 13.32 M 像素页面的 **1.71%**；而 primary 2,223 + borderActive 2,252 + markdownHeading 1,081 + warning 957 + markdownCode 222 + markdownEmph 97 + diffRemoved 80 + syntaxNumber 15 = **6,927 px**。**一条发丝线的墨量 = 全部语义色总和的 32.9 倍。**

行业基准（同为暗色 UI，描边 vs 自身页底）：

| 主题 | 描边 | 页底 | CR |

| warning | #FB8603 | 电 #FAC000（34.40）/ 火（43.89）/ 地（45.20） | 34.40 | — | 32° | ❌ **小火龙橙不是属性色，是角色色** |

**公平地说一条**：语义六元组的**最小成对 ΔE76 = 35.50**（secondary ↔ info），优于官方 18 属性配色自身的最小成对 ΔE76 = 15.22。也就是说，这套语义色**彼此不会互相混淆** —— 这一条设计是成立的。

#### 4.2 但「借用」的边界在哪里？

一个熟悉 Pokémon IP 的评审会怎么判？

- **「primary = 黄 = 电」是站得住的借用**：ΔE00 3.02、色相差 1.4°。Pikachu 是电属性，黄色确实是这个 franchise 的第一主色。这不是撞车。
- **「error = 精灵球红 ≈ 火红」是站得住的借用**：ΔE00 5.64。精灵球是 franchise 的通用符号色，不是属性色，所以拿它当 error 不违反属性语言。
- **「warning = 小火龙橙」是可争议的**：warning 在产品语义里是「注意」，不是「危险」；把它映射到 franchise 里**最负面的属性（火）**，会让熟悉 IP 的人下意识把警告读成「危险/敌人」。而且 **franchise 自己的火色 #E62829 已经被 error 占掉了** —— warning 用的是一个**角色色**，不是属性色。**作者说「语义色来自御三家」，但御三家的橙既不是御三家的属性色，也不是产品的 warning 语义，它是「最广为人知的初代御三家」。** 这是叙事借用，不是类型借用。
- **「secondary = wikiHow 蓝」是全表最弱的一根柱子**：#799DFE 占 2.jpg **55.91%（88,538 px）**，那是**第三方品牌的插画画布底色**（wikiHow 平涂插画），不是任何宝可梦产品面（T 卡 / 图鉴 / 动画 / 周边）上的颜色。它的「出处」在版权语义上恰恰是**最不该拿来当品牌辅色的一类**。而且讽刺的是：这个「辅色」离 franchise 的水属性（ΔE76 16.03）比本主题自己的 `info` 蓝（42.42）**近 2.6 倍** —— 换句话说，**这个 wikiHow 蓝比杰尼龟蓝更像宝可梦的蓝**。作者拿走了那个几何上更对、但出处更弱的颜色；留下那个出处更对、但几何上更错的颜色。

### Q5 · 渲染读起来像「被设计过」吗？

#### 5.1 站得住的部分（要公平）

- **应用窗口整体成立**：侧栏 #060606（L\*1.65）+ 页面 #1C1C22（L\*10.50）分离清晰；diff 行底色 #0A2828 / #0C0406 很克制；警告块（橙字 + 13% 橙底 + 2.5px 橙左边条）是全渲染里唯一一处被验证的「语义色 + 容器」组合，读得出来。
- **正文/次要文案的暖冷分离**：正文 #EEEEF4 冷白，暖意交给金与御三家 —— 方向是对的。
- **`primary` 只做牌不做底**成立：按钮底 #FFCB05 + 字 #141414 = 12.10:1。

#### 5.2 读不出来的部分

| 观察 | 数字 | 判定 |
|---|---|---|
| **纯黑代码台 vs #1C1C22 页底** | 代码体 97.66% 是 #000000，占 feed 列 **13.38%** 像素；Y=0.000 对 Y=0.01193（**≈1.19×10⁷ 倍**，即 1193 万倍）。GitHub 暗色代码底与页底同色（比 1.00×），VS Code #1E1E1E 对 #252526（1.43×） | ❌ **是洞不是面。** 主体最大的暗区不属于阶梯，是一个纯黑真空。 |

| **金标题 vs 金按钮** | ΔE00 **9.70**、互相对比 **1.20:1**、色相差 7.2°、L\* 差 6.63（90.59 vs 83.96）；同窗相距 ≈200 px | ❌ 肉眼读作同一个黄。标题本该是结构，不该是第二块品牌色 —— **违反作者自己的第①条律** |

### 3.3 像素取证面板专项（**核心诚实性通过**）

**a) 命中数会不会被光晕虚增？—— 不会。**

```
analyze(im,w,h)   : 离屏 canvas cx → cx.drawImage(im,0,0) → getImageData → Map<rgbKey,{n,minX,minY,maxX,maxY,idx[]}>
renderOne(...)     : 可见 canvas rec.ctx：先画原图 → globalAlpha=0.58 铺 codeBlockBg 压暗
                     → 命中像素按原色写进 hl canvas，shadowColor=glowHex / shadowBlur=14 叠回
                     → strokeStyle=primary 虚线包围框
```
压暗层、光晕、包围框**只画在可见 canvas**，从不写回 `analyze()` 建的计数 Map；计数键 `keyOf(slot)=parseInt(hex.slice(1),16)` 与 analyze 的 `(r<<16)|(g<<8)|b` 一致。**结论：命中数只能来自源像素，光晕在物理上无法进入计数路径。**

**b) 若某色 0 命中，面板还诚实吗？—— 诚实。**

`select()` 的 0 命中分支：命中区文案改成 `命中 <b>0</b> px · 取证失败` 并加 `.zero` 样式；包围盒区写「该图无此色」；合计行追加 `· 0 命中 = 取证失败`；合计框 `classList.toggle('zero', total===0)`。**不会把 0 说成有。**

**c) selfCheck 是否循环论证？—— 否。**

六项自检中前四项来自**真实像素数据**：参考图载入数 = 4、四图总像素 = 830418（由 `im.width*im.height` 累加）、命中颜色数 = 37（由 Map 的命中记录判定）、零命中颜色 = 0；第五项只校验「颜色来源是 assets.colors 的 37 个」（这是**输入契约**而非结论）；第六项统计运行时错误数。**没有一项是「由定义它的同一份数据证明自己的结论」。**

**d) proof.json 对从零重数 —— 37/37 逐位相同，差 0**（见 §2.8）。
