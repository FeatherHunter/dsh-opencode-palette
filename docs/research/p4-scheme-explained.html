P4 方案说明：非颜色 token 203 + 运行时局部变量 148

2026-10-24 · DeepSeek Harness 宿主基准 rc.3（1f81c04）· 本文件回答「P4 方案是什么」

一句话：P4 是把「底层技术 → 能力上限」里的最后两块没逐条过的技术过完—— ① 公开 token 里除颜色外的 203 条（排印 / 圆角 / 形状 / 材质）； ② 运行时存在的 148 条局部变量（宿主内部、我们改不到，但必须证明「没漏」）。 做完这两块，集合才闭合：425 = 222（颜色）+ 203（非颜色），573 = 425 + 148。

1. P4 在整条主线里的位置

主线是「按底层实现技术逐组讨论，每组出一条一条的能力上限表，最后合成 palette 能力集」。前四组的分工：

轮次覆盖的底层技术产物
P1公开 token · 颜色轴 222 条v3-color-222-ability-map.html
P2私有契约面：--dsl-* 20、--terminal-cursor* 4、哈希类名 156、data-*、inline 74、硬编码色 381 行v3-private-surface-ability-map.html
P3DOM 操作手段（插入图层、换图标、改结构……）v3-dom-ability-map.html
P4（本文件）公开 token · 非颜色 203 条 + 运行时局部变量 148 条v3-noncolor-surface-ability-map.html

P4 之后进入 P5：把 P1–P4 的结论固化成 palette/ 的 9 个 YAML + SPEC（能力条目、值类型、绑定规则、探针、状态）。

2. 为什么 P4 必须做（不做的后果）

  • 不闭合：公开命名空间是 425 条，P1 只过了颜色 222。剩 203 条没逐条过，就不能说「palette 覆盖 DSH 全部可支持上限」——用户 U1 的裁定是「必须包含上限，用不用另说」。
  • 会漏能力：排印 182 条里藏着「按内容角色改字号 / 行高」的落点；radius 6 条是圆角；menu / corner / mask 是材质与形状。这些不是颜色，但都是用户能感知的效果。
  • 会错判：运行时还有 148 条变量（宿主内部布局量、组件私有实现）。不登记就无法回答「我的主题为什么改了没反应」——其中绝大多数是「写在 body 上无效」的。

3. 分类判据（第一性原理）

不是按「名字好不好看」分类，而是按「写入之后宿主会不会真的变」分三类：

类含义在 P4 里的条数处理方式
A. token 写入即生效宿主在 body 级声明、消费方读这个变量排印复合 30（其中 live 18）、radius 6、menu 材质 1直接成为能力条目（直绑定 + 语义 id）
B. token 写入无效，需要规则层宿主不消费该变量，或元素级重声明盖住排印长手 150（dead 139）、--dsw-mask-blur（钉死 none）登记 + 标 dead / gated；不冒充可用；改字号/行高走规则层按内容角色
C. 不建用户能力，只登记元素级作用域 / JS 内部写入，body 覆盖无效--dsh 11 + 运行时 148进登记表，注明「不开放、原因、证据」

4. 每一条长什么样（逐条格式）

203 条每行都有：

列回答的问题
token 名 / 中文名这个底层技术叫什么、给人看的中文是什么
状态 + 修饰live（有消费方）/ dead（宿主不读）/ gated（元素级重声明）/ declared_invalid（声明与读取位置不一致）
消费位置与次数宿主哪里在用它（文件 + 行号 + 次数），以后不用翻源码
值类型能写什么：长度 / 字体栈 / 字体资源 / 数字 / 颜色 / 材质 / 形状
能力 id用户在 theme.yaml 里写的稳定名字，如 typography.composite.headingL、radius.card
能改什么效果一句话说明用户能感知到什么
tier / 暴露stable（正式）/ advanced（高级·默认折叠）/ experimental（实验）/ dead（不可用）
探针加载时怎么判断「宿主还认不认这条」：token_live(name) 等

  • radius 6 · --dsh 11 · menu 材质 1 · corner 形状 1 · mask 1 · 焦点环宽度 1
  • 合计 live 52 / dead 151
  • 203 条 capability_id 全部通过文法 + 能力域校验：0 违规、0 重名；新增能力域 typography / radius / runtime / mask（能力域总数 29 → 33）

运行时局部变量 148 条：

  • --dsh 额外 60 + --dsl 20（P2 已过）+ 其他包局部 --dsw 12 + 组件局部其它 56 = 148
  • 口径 = 2026-10-20 安装版首屏 Playwright 实测；证据已入库 scripts/research/data/runtime-scan-web-2026-10-20.json
  • rc.3 已确认主题面零变更（CSS 文件 SHA256 全同、0 增删声明）；运行时数字在 P7 升级演练时复测

集合闭合：425 = 222（P1 颜色）+ 203（P4 非颜色）；573 = 425 + 148（运行时）。

6. 设计取舍与诚实边界

不冒充可用：150 条排印长手里 139 条是 dead（宿主只声明、不读取）。我们把它们登记为 dead、默认不暴露；如果未来宿主开始消费，扫描器改状态即可，不需要改用户文件。

运行时 148 不建用户能力：它们要么是元素级作用域，要么是 JS 写入（如终端光标、布局量），body 级写入无效。登记目的只有两个：不再翻源码、证明没漏。

排印的「可改」落在两处：① 30 个复合 token（写入即生效，做「整体字号 / 行高」）；② 规则层按内容角色（p / h1 / code / blockquote，做「某类内容单独改字号 / 行距」）。后者属于 P3 的规则手段，两者在主表里合成同一条能力。

死名 ≠ 永久死：状态由扫描器按宿主源码生成，宿主升级后重扫即可；用户 theme.yaml 不受影响。
