1.2 为什么「留到升级时更好」：这正好是 yaml 掌管升级的真实演练

演练流程（升级那天照做）：

  1. 把预览/测试宿主升到 rc.3（或正式版）；
  2. 重跑 python scripts/research/gen_token_registry.py → palette/tokens.yaml 整表刷新；
  3. 重跑锚点扫描（palette:scan-anchors，实现期）→ palette/anchors.yaml 刷新；
  4. 生成 diff 报告：新增 / 删除 / 改名 / 活死状态变化 / 新 slot / 选择器失效；
  5. 看主题文件：用户 theme.yaml 一个字都不用改（模板/主题靠稳定 id + palette 别名链适配），只有 palette 层更新；
  6. 编辑器据此提示「宿主已升级，X 个能力需重新绑定 / Y 个新能力可用了」。

验收判据（这次升级就验这 4 条）：

#判据失败说明什么
1升级后重跑扫描器，时刻数字自动更新（零手改）扫描器有硬编码
2已有 theme.yaml 主题零修改仍能加载主题与宿主名耦合了
3宿主改名/删名 → 诊断出清单，不静默崩别名链/探测没兜住

结论：rc.3 运行期测试不是「不做」，是挪到升级演练里做，并且升级演练本身是 V3 的验收项（U20-②「四道验收」里的「上游升级不炸」）。现在把 rc.3 的静态结论写进规则约束即可。
