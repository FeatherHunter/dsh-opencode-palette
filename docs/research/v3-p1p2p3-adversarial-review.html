对象：v3-color-222-ability-map.html（P1）、v3-private-surface-ability-map.html + v3-anchor-surface-map.html（P2）、v3-dom-ability-map.html（P3）。方法：从第一性原理定义「完备」的四条件，再逐条找反例。结论先说：素材是对的，但这三份合起来还不是「完备方案」——不是数据错，而是缺了三层东西（能力主表、运行态验证、非颜色面清点）。

C5需求可溯源用户 24 条 idea 每条都能追到 ≥1 个能力，能力也能反追到需求；不在能力表里的需求有显式「不做/延后」理由

2. P0 级漏洞（4 条）

P0-1　能力 id 与现行词表脱节：P1 只有 2/222 能通过语法校验

证据：按 palette/vocabulary.yaml 当前文法（region.role.property，region ∈ 14 区、role ∈ 27 角色、property ∈ 16 属性）严格校验 P1 的 222 个「建议语义能力」：

valid   = 2      （global.page.background / settings.card.background）
invalid = 220
  - 首段不是 14 区之一：179 条（content / control / status / atom / effect / region /
    onboarding / overlay / document / decor / tooltip / toast / selection …）
  - 不是 3 段：125 条（2 段到 6 段都有，如 atom.blue-500、content.code.syntax.string-expression）
P2 同问题：--dsl 的 20 个建议 id 中 19 条首段是 content（不是 14 区之一）。
P3 同问题：20 条能力里 8 条是 4 段（global.page.background.media），
          3 条带占位符（control.<control>.icon / structure.<target>.hidden）。

为什么严重：scripts/research/palette-check.py 正是按现行词表校验 id 的；照现在三份表直接落成 palette 条目，checker 会大面积报错，或者我们会被迫放宽 checker——两种都违背你「零偏差」要求。

修法（需要你裁一次）：三选一——A 扩词表（新增 region：content/control/status/atom/effect/entry/structure/onboarding/selection；新增 role/property 若干）；B 保留词表，把三份 id 全部映射到现有 14 区（会损失精度）；C 承认有「语义菜单层」与「palette 绑定层」两套 id，加映射表（多一层维护）。我倾向 A，因为你的目标是「全量能力集」，词表本来就该跟着能力扩张。

P0-2　缺「能力主表」：三份是技术视角，不是能力身份视角

证据：同一视觉效果在 P1/P2/P3 里各出现一次，且 id 不同：

视觉效果P1（token）P2（私有变量）P3（DOM）

为什么严重：你 m02823 定的是「我们维护的是能力到底层实现技术的映射（token 只是底层实现技术的一部分）」。但三份表是「技术→能力」的反向列表；没有主表就无法回答「这个能力到底用哪条技术实现、失败时降级到哪条」，也无法避免编辑器里出现两个开关控制同一个效果。

修法：新增能力主表（palette/capabilities.yaml 的候选）：一条 capability = { id, 用户文案, 值类型, tier, 实现技术链[按优先级：token → rule → dom → runtime], 每步的 probe/teardown, 验收断言 }。P1/P2/P3 降级为「技术证据层」，不再新增能力 id。

P0-3　锚点未经验证：P3 至少 3 个「猜出来的选择器」

证据：扫描宿主 rc.3 源码字面量只找到 3 个 data-slot 值（conversation.chat.flow / <key> / root）；P3 能力表里用的：

P3 里的锚点源码验证结论

[data-menu-material]ui-primitives/src/MenuSurface.tsx 有✔ 真实
[data-conversation-region]ConversationContent.tsx / stop-shortcut.ts 有✔ 真实

为什么严重：锚点是「绑定可达」的全部；猜错 = 能力静默不生效，且我们的 probe 如果也写成同一个猜测，就永远发现不了。要求：每条锚点标注 source-literal / runtime-verified / dynamic / guess，guess 不得进 palette；P3 里 guess 的条目必须先用 Playwright 实跑确认。

P0-4　集合未闭合：425 里还有 203 个非颜色 token 未进任何表

证据：palette/tokens.yaml 全量 425 按 family：typography 182、alias 107、static 77、specific 11、shiki 11、dsh 11、radius 6、elevation 5、shadow 4、gradient 3、linear 2、focus 1、menu_color 1、menu 1、corner 1、mask 1、other 1。P1 只做了颜色轴 222；剩下 203 条（typography 182 + radius 6 + menu 1 + corner 1 + mask 1 + other 1 + dsh 11）在 P1–P3 里没有任何「能力行」，只有 P4 计划要覆盖字体/字号/行距。

另外三类「不在 425 但运行时存在」的面也没进统一清点：--dsh-* 运行时 71（布局量，含可做的字号 3 个）、其他包局部 --dsw 12、组件局部变量 56；P2 只覆盖了 --dsl-* 20 与 --terminal-cursor* 4。

修法：把 P4 扩成「非颜色 203 + 运行时 139」两节；并在 P1–P3 封面写明「本表覆盖 X/425，剩余见 P4/待办」，否则读者会误以为已经全量。

3. P1 级缺口（7 条）

  1. 状态/修饰机不一致：P1 里 --shiki-foreground / --shiki-background 标 live 无修饰，但 color-axis-token-inventory.md §5 明确它们属于 declared_invalid（在 :root 引用 body 级 alias，计算期无效，靠 fallback/JS 才有值）。→ 要么改状态，要么在表头注明「P1 只按 CSS var() 消费判定」。
  2. 「0 消费却 live」无解释：shiki 9 个 token 由 shiki 运行时消费，CSS 扫描看不到；P1 若显示消费 0 又标 live，读者无法自证。→ 加列「消费来源：CSS / 运行时 / JS」。
  3. tier 词表不统一：P1 用「稳定 / 高级·原子 / ⛔不生效」，U7 定的是 stable / experimental；P3 又混入「正式/实验」。→ 统一 3 值：stable / experimental / dead（+ 修饰 gated）。
  4. 直绑定 id 规则未定义：P1 写「直绑定 id = token.<name 去 -- 换 .>」，但现行文法没有 token.* 命名空间，checker 也不认。→ 定义 token.* 为生成命名空间并写进 grammar。
  5. 颜色能力缺「暗/亮成对」与「自动对比度」约束：P1 每条只有一个值位置，没有声明「必须 light/dark 成对」；--dsw-* 全部是成对的。→ 在能力主表里给值类型加 diurnal: true（P1 表未体现）。
  6. P1 的「能改什么」是自然语言，不是可执行断言：没有 per-row probe（如「设置后 getComputedStyle(body).backgroundColor = 期望」）。→ P4 前给 222 条补 probe 模板（按区域批量）。
  7. 缺需求溯源：222 条颜色能力没有一条反追到 24 条 idea（比如第 20 条「点赞颜色分类排序」对应哪些能力？）。→ 见 C5。

4. P2 级（6 条）

  1. 数字口径三套并存：硬编码色 381 行（本次 packages+apps 含 desktop）vs 旧文档 351（client only）；data-* 290 源码名（本次）vs 旧 432 vs 运行时 51；--dsl 20（含 2 条仅消费）vs 口头 19。→ 每个数字加脚注「扫描范围」。
  2. fallback 13 的定义：13 是「含 rgba 的色 fallback」；只算 #hex 是 7。→ 表头写清判据。
  3. 「--dsl 改上游即可」未逐条证明：11 条有上游，7 条结构性值没有上游 token（字体/圆角/行高/换行），需逐条给「值从哪来、不改上游时靠什么规则」。
  4. 1 条来源不明：--dsl-code-block-line-number-width 只找到消费、没找到声明。→ 追到声明处或标「死变量」。
  5. 锚点层缺 runtime 全量：源码字面量 data-slot 只有 3 个，但 rc.3 运行态约 43 个（动态注入）。→ 跑一次 Playwright 拿 data-slot 全量值，替换「源码字面量」表。
  6. 哈希类名 156 未枚举：策略有了（后缀匹配），但没有清单 → 无法验证哪些能力依赖它们。→ 输出 top-N 哈希 local 名 + 出现区域。

6. 建议的修复顺序（不改变已认可内容）

  1. 先裁 P0-1（词表三选一）——它决定后面所有 id 怎么写；建议 A 扩词表。
  2. 建能力主表（P0-2）：三份技术表变成证据层；这一步不改动任何「能做什么」的结论，只改组织方式。
  3. 跑一次运行态锚点验证（P0-3 + P2-5）：Playwright 拿 data-slot / data-* 全量 + 抽 10 条能力做「设置→断言→撤销」。
  4. P4 扩为「非颜色 203 + 运行时 139」（P0-4），并按 topic 出表。
  5. 补四件横切规范（P2 级）：口径脚注、tier 词表、probe 模板、需求溯源矩阵。
  6. 最后才做零偏差审计与 #147 收口——否则审计对象还不完备。
诚实结论：「科学没有遗漏」目前不成立：按上面 5 条完备性条件，C1 集合封闭 ❌（缺 203+139）、C2 语义单义 ❌（跨技术同效果无主表）、C3 绑定可达 ⚠️（3 个假锚点、运行态未验）、C4 可验可测 ❌（P1/P2 无 probe）、C5 需求可溯源 ❌（无矩阵）。但这些都是组织与验证缺口，不是「能力判断错了」——三份表作为素材可以继续用，只需要按上述顺序补壳。
