一、elevation 5 条：为什么写 token 不够，必须再加规则层

1. 它是什么

elevation 是宿主的「浮起材质」预设——不是颜色，而是「阴影 + 0.5px 描边」的组合值，用来表现「面板浮在页面上」的层次感（弹窗、命令面板、附件卡片、对话输入区等）。

token消费处数主要影响区用户感知
--dsw-elevation-prominent18对话主窗口、命令面板最强调的浮起（弹窗/命令面板）
--dsw-elevation-panel11基础组件、附件普通面板浮起
--dsw-elevation-stroke3主题自身浮起物外描边宽度
--dsw-elevation-soft2会话/输入区、Markdown更轻的浮起
--dsw-elevation-stroke-color1主题自身描边颜色

Android 类比：它更像每个 View 的 android:elevation（逐控件属性），不是一个全局主题色。

2. 为什么「只写 token」改了没反应

宿主不是在 body 上声明一次就完事，而是给页面上每个元素都声明了一份（样式表原文，packages/client/ui-theme/src/styles/gradient-shadow-text.css:31-40）：

/* 宿主真实写法（简化） */
body, body * {
  --dsw-elevation-panel: <阴影值>;
  --dsw-elevation-prominent: <阴影值>;
  --dsw-elevation-soft: <阴影值>;
  --dsw-elevation-stroke: <描边>;
  --dsw-elevation-stroke-color: <颜色>;
}

而我们的 A 通道（theme.overrideTokens）只能写 <body style="--dsw-elevation-panel: …">。问题来了：body 上写的值只作用于 body 自己；它下面的每个子元素都有一份自己的同名声明，子元素那份覆盖父级继承——所以页面上真正显示的仍然是宿主原来的值。

/* 实测：body 上写入 token 后，元素上仍是宿主自己的声明 */
<body style="--dsw-elevation-panel: 0 4px 12px red">
  <div class="…">   /* 这个 div 自己声明了 --dsw-elevation-panel，body 的值传不进来 */

3. 「需规则层」= 我们额外写一条 CSS 规则

所以这个能力在我们的能力条目里会写成两条写（write）：①token 写（给 body，覆盖没被元素声明的场景）②规则写（命中元素，真正生效）：

/* 我们的规则层（放进 <style>，且晚于宿主样式） */
body, body * {
  --dsw-elevation-panel: 0 4px 12px rgba(0,0,0,.18) !important;
  --dsw-elevation-prominent: 0 8px 24px rgba(0,0,0,.22) !important;
}

用户仍然只在编辑器里看到一个「浮起材质」能力（改强度/预设），内部自动双写。能力是稳定可用的，所以 tier = 稳定；只是「实现技术」一栏写的是 token + rule，不是纯 token。

风险与限制（实现时要处理）：
  • 性能：body * 规则影响全页元素，需要保守数量；不会每个元素都重算布局，但样式匹配有成本。
  • 局部重绑：宿主的 --dsw-elevation-stroke-color 还在 ≥10 个组件里被单独重绑（如 ui-attachment/AttachmentRail.module.css:95、ui-chat/chat/ChatView.module.css:287、ui-conversation/skeleton/InputBar.module.css:60,83），这些组件里我们的规则可能被盖住——验收时要逐个点开弹窗/附件/输入区确认。
  • 不做 reduced-motion 适配（你已裁：不加开关、不写代码）。

二、static 77 个原子：为什么标「高级·默认不直接暴露」

1. 它是什么

宿主的颜色是两层的：

底层原材料（static，77 个纯色 hex）
   --dsw-static-blue-500: #3b82f6;      ← 77 个之一
        ↓ 被引用
语义色（alias，107 个）
   --dsw-alias-button-primary-fill: var(--dsw-static-blue-500);
        ↓ 被组件消费
界面上的按钮 / 链接 / 状态点

证据：宿主 design-platform.css 里 202 条 alias 定义中，138 条的值直接是 var(--dsw-static-*)，涉及约 55 个不同的 static。77 个 static 里：live 60dead 17（17 个没有任何消费方，写了也不生效）。

2. 为什么默认不直接暴露给用户

因为改一个原子，会连锁改掉所有引用它的语义色。比如把 --dsw-static-blue-500 从蓝改成紫，可能同时改掉：按钮主色、链接色、选中态、焦点环、状态信息色……用户以为只改了一个「蓝」，实际整站配色都动了，还很容易把对比度改崩。

而用户 99% 的意图是「页面底色、正文颜色、按钮颜色」这类语义色——这些在 P1 的表里已经有对应能力（如 global.page.background）。

3. 我们的处理（既满足「全量收录」，又不误导）

  • 全量登记：77 个原子全部在 palette/tokens.yaml 里，一个不少（你的「425 个都要有」要求）。
  • tier = 高级 · 默认折叠：编辑器里默认不展开，收在「变量表 / 专家区」；不放在常用能力列表里。
  • 一个 token 一个语义：每个原子也各有一个语义 id（如 atom.blue-500），不合并。
  • 写时提示：选中原子时提示「这是底层原材料，会影响 N 个语义色」，并把受影响的语义色列出来。
  • 死原子 17 个：标「不生效」，可写但没有任何视觉变化（保留记录，不删）。

4. 一句话总结

elevation 是「实现技术要多一步（规则层）」，能力稳定；static 是「风险高、层级低（原材料）」，所以默认折叠。两者都不删、不合并、全量登记，只是 tier 与入口不同。
