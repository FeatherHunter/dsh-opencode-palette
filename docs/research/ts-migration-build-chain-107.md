# tsc / esbuild 产物 × 零依赖 mini-bundler：兼容性测绘（#107）

> 研究子票：#107（wayfinder 地图 #104）。
> **结论先行**：不改 bundler 语义的前提下，最近的可行路径是 **先放宽 4 条行级正则（B），再让构建器读 tsc emit 的 JS 中间层（C-lite）**；其中 **B 单独成立、且是事实上最省风险的一步**——它覆盖的不只是「以后迁 TS」，还有「现在任何人跑一次带分号的格式化」这个真实脆弱点。

## 1. 问题

本仓没有 bundler 依赖。`scripts/build-client.mjs`（406 行）用「逐行正则 + `__mods` 模块表 + 手写 `MODULE_ORDER`」把 `src/engine/*.mjs`、`runtime/*.mjs`、`src/themes/*.json` 拼成两个入口形状，另有一条独立通路把 `node_modules` 里两个钉版包的内联进来。

问题：**如果源码换成 tsc emit 或 esbuild 的产物，这个构建器还撑不撑得住？** 拆成四问：

1. 它依赖哪些文本级假设？逐条精确到行。
2. 换成 tsc / esbuild 产物后，哪条会破、破在哪行、失败方式是什么（构建报错 / 静默产坏 bundle / 只是体积格式变化）？哪些假设对「tsc 单文件转译、`module: NodeNext`、保留 `.mjs`」其实兼容？
3. 可行改造路径 A/B/C/D 的改动面、确定性、与 `DESIGN.md` §7「零依赖、不引 esbuild/rollup、产物确定无版本漂移」的关系，以及 v1.2.0 ASI 事故的教训。
4. 新旧 bundle 行为等价怎么判？哪些差异可接受？

## 3. 构建器逐层解剖

### 3.0 数据流

```
src/engine/*.mjs + runtime/*.mjs
  └─ readSource(): readFile → CRLF→LF                    (218-222，调用点 227/232/339)
      └─ loadModule(): split('\n') → 5 条正则逐行消解      (224-283)
          └─ 每模块包 IIFE，导出写 __mods[key]            (279-282)
              └─ bundleModules(): 按 MODULE_ORDER 拼接    (117-126, 210-216)
                  ├─ 包版模板 → package/lib/client.js     (302-325)
                  └─ 动态版模板 → client.js               (328-335)
runtime/host.mjs ──原样复制──→ package/lib/index.js        (337-339, 387-388)
```

另一条**完全独立**的通路：`node_modules/{dsh-log,dsh-plugin-update}/dist/*.js` → `transformPackageModule`（154-197）→ 同样的 `__mods` 形态。两条通路对「编译产物风格」的容忍度**不一样**，这是本文的关键对照（§4.5）。

### 3.1 输入层

| 假设 | 证据 | 说明 |
|---|---|---|
| 输入是 UTF-8 文本、行尾是 LF | `scripts/build-client.mjs:218-222` | `readSource` 做 `replace(/\r\n/g,'\n')`。`.gitattributes` 全文只有一行 `* text=auto`，Windows 检出即 CRLF；不归一则 `$` 匹配不到行尾 `\r`，**所有**行级正则集体失效（注释 218-219 与 `DESIGN.md:141-142` 都写明这条，并把后果说成「新克隆上构建静默产出 broken bundle」） |
| 宿主半不做语句级转换 | `scripts/build-client.mjs:337-339` | 只 `readFile` + CRLF 归一，原样写进 `package/lib/index.js`（388）。注释 337：「版本已在源码里读自己的 package.json，无需注入」 |
| vendor 表是固定相对路径 | `scripts/build-client.mjs:37-104` | 39 个模块（dsh-log 22 + dsh-plugin-update 17）。deps 的键必须是**包内 import 的原字面量**（注释 42-43：`'../core/ids.js'` 与 `'./core/ids.js'` 是两个键，不能归一） |

### 3.2 词法与语句层——全部脆弱性集中在这里

`loadModule` 是一个 `for (const line of text.split('\n'))`（233），每行依次试 5 个模式，**都不中就 `body.push(line)` 原样送进 IIFE**（279 之前）。这个「忘了就透传」的设计决定了失败方式：漏匹配不等于报错，等于把 `import` 语句塞进函数体。

五条模式：

| # | 模式 | 代码 |
|---|---|---|
| 1 | JSON import | `scripts/build-client.mjs:128` `/^import (\w+) from '([^']+\.json)' with \{ type: 'json' \}$/` |
| 2 | 相对 JS import | `:129` `/^import \{ ([^}]+) \} from '\.\/([A-Za-z0-9_\/-]+)\.mjs'$/` |
| 3 | 包 import | `:130` `/^import \{ ([^}]+) \} from '([a-z0-9-]+\/[a-z0-9-]+)'$/` |
| 4 | 行内导出 | `:131` `/^export (function|const) (\w+)/` |
| 5 | 整行重导出 | `:272` `line.match(/^export \{ ([^}]+) \}$/)` |

### 3.3 图与顺序层（静默风险面）

- **模块键 = 文件 basename**：`scripts/build-client.mjs:255` 把 import 的路径段整个丢掉，`const { … } = __mods[' + q(m[2].split('/').pop()) + ']`。所以 `runtime/client.mjs:4` 的 `from './engine/index.mjs'` 被解析成 `__mods['index']`——目录前缀不参与身份判定。
- **相对 import 的依赖顺序由人维护**：`scripts/build-client.mjs:117-126` 的 `MODULE_ORDER` 是手写全序（39 个 vendor 键 + 14 个引擎键 + 6 个 runtime 键 = 59），注释 116：`// 模块执行顺序 = 依赖顺序（模块顶层不得调用其他模块导出，见 DESIGN.md）`。**没有任何自动校验**这条全序是不是依赖图的线性扩展。
- **JSON 也是 basename 查找**：`:241-249`，先 `THEMES_DIR/<base>`，只有 `ENOENT` 才回退 `CUSTOM_PRESETS_DIR/<base>`（所以主题与 IP 预设不能同名）。

### 3.4 生成层（`__mods` 协议与模板）

- 每模块产出 `(function () {\n … \n})();`（282），导出在末尾写成 `__mods[key] = { a, b }`（279-281）。
- 包版模板（302-325）把 `__mods` 声明在 `factory` 内，末尾 `exports.apply = __mods['client'].createClient('settings.plugins.tab')`（321）；动态版（328-335）末尾 `return { apply: __mods['client'].createClient('tool.view.cordis') }`（334）。
- **v1.2.0 事故的注释就长在这里**：`scripts/build-client.mjs:315-318` 写明 `var __mods = {}` 必须带分号——否则下一行模块 IIFE 的 `(function () {` 会被解析成对 `{}` 的函数调用，抛 `TypeError: {} is not a function`。动态版同一坑在 331-332 另注一遍。
- 版本注入：`:293` `(await bundleModules()).split('__PALETTE_VERSION__').join(version)`；占位符全仓只有一处使用点 `runtime/client.mjs:26`。

`:382-403`：先清 `package/node_modules` 与 `package-lock.json`（383-384）→ 复制 `cordis.patch.yml`（386）→ 写 `lib/client.js`（387）、`lib/index.js`（388）、`lib/event-list.json`（389）、`lib/channel.mjs`（391）→ 写 `package/package.json`（392）→ 从 `docs/README.en.md` 删 showcase 块后写 `package/README.md`（395-397）→ 写根 `client.js`（398）。`package.json` 是**字面量**（342-380），含精确钉版 `dsh-log@0.3.4` / `dsh-plugin-update@0.18.11`。

## 4. 对 tsc / esbuild 产物的兼容性矩阵

### 4.1 tsc emit（`module: NodeNext`，`.mts → .mjs`）

tsc 的 emit 风格用本仓 `node_modules` 的两个真实样本锚定，不靠推测：

- **必加分号**：`node_modules/dsh-log/dist/config.js` 通篇是 `export { listLogFiles, logFilesOfDate, matchExportFileName, parseLogFileName } from './core/file-name.js';`
- **引号不由 tsc 决定**：同一个 `node_modules` 下，`dsh-log/dist` 用单引号，`dsh-plugin-update/dist` 用双引号（`import { DEFAULT_PREFIX, MIN_PANEL_POLL_MS, buildPhoneNames } from "./config.js";`）。两边首行都自报 `Source: src/*.ts`。**结论：不能假设单引号。**
- **可能多行 import**：`node_modules/dsh-plugin-update/dist/entry.js` 有 `import {\n  failureCodeOf,\n  mountUpdatePanel,\n  normalizePanelTheme,\n  themeTokensStyleFor\n} from "./panel.js";` —— 这是源码本来就多行，tsc 照抄换行。

| 假设 | 是否破 | 破在哪 | 失败方式 |
|---|---|---|---|
| A2 单行 import | **不破**（前提：源码保持单行） | — | 若源写成多行，只有首行 `import {` 不匹配任何模式 → 原文进 IIFE → **加载期 SyntaxError** |
| A3 无分号 | **破（致命）** | `:128` `:129` `:130` `:272` 的 `$` | 94 条 import 行 + 1 条 reexport 全部落空 → 原样进 IIFE → **构建 exit 0，加载期 SyntaxError**（与 v1.2.0 同类失败） |
| A4 单引号 | **破或半破** | `:128,129,130` 的 `'` | 同上（silent → SyntaxError） |
| A5 `with { type: 'json' }` 精确 | **破** | `:128` | 同上；且 tsc 对 import attributes 的引号/空格是否规范化未验证（§8） |
| A6 JSON basename 查找 | 不破 | — | 与 emit 风格无关（JSON 由 `THEMES_DIR` 直接读，不读 emit 出来的 JSON） |
| A7 `.mjs` 扩展名 | **破，且与分号独立** | `:129` 的 `\.mjs` | 若源是 `.ts`（根 `package.json:2` 是 `"type": "module"`），NodeNext 下 emit `.js`、源码必须写 `'./x.js'` → 34 条全灭 → 原文进 IIFE → SyntaxError。**想保住 `.mjs` 必须以 `.mts` 为源** |
| A8 basename 身份 | 不破（但静默风险） | `:255` | tsc 保留目录结构，正常不会撞名；一旦撞名，`__mods[key]` 被后写覆盖 → 运行期 undefined，**构建不报错** |
| A9/A10 包 import | 不破 | `:130,258-263` | 唯一的例外：开 `importHelpers` 时 tsc 会插 `import { __awaiter } from "tslib"` —— 单段 specifier 不匹配 `[a-z0-9-]+/[a-z0-9-]+`，且未登记 → 兜底进 IIFE → SyntaxError（tslib 也不在依赖里） |
| A11 无 `as` 别名 | 不破（前提：源码不引入别名） | `:255` | 若出现 `import { a as b }`，`const { a as b } = …` → SyntaxError。**埋着的坑**：批量重构/自动 fix 若引入别名，构建静默坏 |
| A12 导出形态 | **条件破** | `:131` | `target < ES2015` 时 tsc 把 `const` 降级成 `var` → `export var X` 不匹配 → 原文进 IIFE → SyntaxError。`target: ES2022` 则完全不破 |
| A13 `export { … }` | **破（致命）** | `:272` | tsc 只补一个 `;`。这是全仓唯一一条（`src/engine/index.mjs:43`），也是 `runtime/client.mjs:4` 拿 17 个名字的唯一出口——破就是整包黑屏 |
| A14 `__mods` 协议 | 不破 | — | tsc 不改变语句结构 |
| A15 顺序 | 不破 | — | 源码顺序不变；但若改读 `dist/`，`MODULE_ORDER` 的键必须与 dist 文件名一致，否则 ENOENT（fail loud，可接受） |
| A17 宿主半 | **不破，但要跟扩展名** | `:339,391` | `host.mts` emit 后仍是真 ESM，可原样复制。若走 `.js` 方案，`host.js` 里写 `import './channel.js'`，则 `:391` 的 copy 目标要从 `lib/channel.mjs` 改成 `lib/channel.js`（1 行） |
| A19 版本占位符 | 不破 | `:293` | tsc 保留字符串字面量；一开 minify/常量折叠就失效 |
| A20 产物契约 | 不破 | — | — |

**对 tsc 单文件转译其实兼容的部分**（不用改）：A2（保单行）、A6、A8、A9/A10、A14、A15、A16、A17、A19、A20。真正要动的只有「标点 + 引号 + 扩展名」三件事，落点只有 4 条正则 + 1 个字符类。

### 4.2 esbuild（bundle 形态）

| 输入形态 | 结果 | 失败方式 |
|---|---|---|
| `--bundle` 单文件（任意 `--format`） | **构建立刻失败** | `bundleModules()`（`:210-216`）按 `MODULE_ORDER` 的 59 个键去 `ENGINE_DIR/<key>.mjs` / `RUNTIME_MODULE_FILES` 找文件，单文件下全部 ENOENT。**fail loud，这是最好的失败** |
| `--bundle --splitting` 多 chunk | 构建期 ENOENT 或（若强行只换 engine 目录）chunk 间 `import './chunk-XXX.mjs'` → basename `chunk-XXX` 不在 `__mods` → 运行期 `undefined` | 静默 → 运行期 TypeError |
| `--bundle --format=cjs` + 手写入口 shim | 技术上可能跑通（`factory(require)` 里提供了 `module`/`exports`/`require`），但**消灭逐模块键** | `exports.apply = __mods['client'].createClient(…)`（`:321,334`）→ `TypeError: Cannot read properties of undefined`；同时 `tests/update-panel.test.mjs:208-224` 对 `__mods["upd-entry"]` 的 5 条文本断言全红 |
| `--minify` | 单行，全灭 | 加载期 SyntaxError |

### 4.3 esbuild（逐文件 transform，不 bundle）

与 tsc emit 同构：**加分号、可能改引号、可能压行或展开**。所以 A3/A4 的破法与 §4.1 完全相同。差别只有两点：esbuild transform 保留输入扩展名（`.mjs` 进 `.mjs` 出），所以 **A7 不破**；反过来 tsc 在 `.ts → .js` 下更麻烦。

实测（只读）：`import{TOKEN_MAP as e}from"./map-dsh.js";` 与 `export{createClient};` 两形态对 5 条模式**全不命中**。其中 `export{createClient};` 尤其危险——它连 `:131` 的 `^export (function|const)` 都不匹配，且**不含空格**，肉眼极难扫出来。

### 4.4 失败方式分级（用来判断改造优先级）

| 级别 | 表现 | 例子 | 评价 |
|---|---|---|---|
| L1 | 构建期硬失败 | esbuild bundle 的 ENOENT；`:195` 的「未处理的 export 形态」；`:261` 的「未登记的包引用」 | 好——改完立刻知道 |
| L2 | 构建期静默、加载期 SyntaxError | 分号/引号/扩展名导致 import 与 export 原样进 IIFE | **坏，与 v1.2.0 同类** |
| L3 | 构建期静默、运行期 undefined/TypeError | basename 撞名、`MODULE_ORDER` 漏项、import 别名 | **最坏**——可能是局部功能静默失效 |
| L4 | 只是字节数/格式/体积变化 | 注释保留、缩进、source map 注释 | 可接受（§6 白名单） |

### 4.5 关键对照：vendor 通路早就吃过这个亏

`transformPackageModule` 用的三条正则**已经**带 `["']` 与 `;?`：

- `scripts/build-client.mjs:133` `PKG_ESM_IMPORT_RE = /^[ \t]*import\s*\{([\s\S]*?)\}\s*from\s*["']([^"']+)["'];?/gm`
- `:134` `PKG_ESM_EXPORT_RE = /^[ \t]*export\s*\{([\s\S]*?)\};?/gm`
- `:136` `PKG_ESM_EXPORT_FROM_RE = /^[ \t]*export\s*\{([\s\S]*?)\}\s*from\s*["']([^"']+)["'];?/gm`

而且 `:195` 有兜底：`if (/^[ \t]*export[\s{]/m.test(out)) throw '[build] vendor 模块有未处理的 export 形态：'`——**fail loud**。

也就是说：同一个仓库里，面对**编译产物**的那条通路已经加固过了（容忍分号、双引号、多行、`as` 别名），引擎通路没有。这不是设计缺陷的猜测，是一份仓内的对照实验——作者付过一次学费，只是没回灌。

### 5.2 v1.2.0 教训对各路径的映射

事故根因不是「分号写错」，而是 **文本生成器的缺陷在构建期不可见**（`scripts/build-client.mjs:315-318`）。

- A 增加一层文本变换 → 与教训**反向**（多一个构建期不可见的环节）。
- B 不消除该类根因，但把 4 条 `$` 从「脆」变「韧」，让「加个分号」这种无害输入不再变成坏产物——**减小了触发面，而不是消除**。
- C 换了输入源，触发面取决于 tsc 的稳定性，比 A 可控。
- 真正消除根因要靠 §6 的 L1/L2/L3 门禁（构建后验证），不靠任何一条输入路径。

## 6. 产物等价性验证方案

现状：字节哈希只能证明「同输入稳定」，**证不了新旧等价**（§4.1 里 tsc 会改引号/分号，字节必然不同）。分层设计：

| 层 | 判据 | 成本 | 能做/已有 |
|---|---|---|---|
| **L0 可重复性** | 同一输入连跑两次 build，`client.js` / `package/lib/client.js` / `package/lib/index.js` 三份字节相等；LF 与 CRLF 两种检出下相等（A1 已保证） | 极低 | 现在就能做，一行 `git diff --stat` |
| **L1 导出面 diff** | 从两份产物抽 `__mods["k"] = { … }` 的键集合、每键导出名集合、`__mods["k"]` 的读取点，做双向差集。要求：键集合相同、每键导出名集合相同、被读的键都在读之前被赋值 | 低（~60 行、零依赖） | 新写。这是最划算的一道门禁，能抓住「正则放宽后误吞某行」 |
| **L2 拓扑校验** | 把 `__mods[dep]` 的读取边抽成图，验证 `MODULE_ORDER` 是它的线性扩展 | 低 | 新写。有了它，「模块顺序变了」才可判为安全 |
| **L3 语义金样** | 38 主题 × 2 模式 × {`renderTheme`, `previewColors`, `auditAll`} 的金样 JSON，新旧逐字段 diff | 中 | 可复用现有引擎 API（`tests/engine.test.mjs` 已直连源码） |
| **L4 端到端** | 262 个顶层 `test()`（`^test\(` 计数）全绿 + `tests/panel-render.test.mjs` 的 45 个 `renderToString`（React 18.3.1 真实渲染，产物经 `vm.runInThisContext` 加载） | 已有 | 现成，是最强的语义 oracle |

**可接受差异白名单**：字节数/行数、空白与缩进、注释保留与否、引号风格、语句尾分号、模块间空行、source map 注释（`--inlineSourceMap` 会让体积暴涨，仍算可接受但应避免）；模块体顺序（**仅当 L2 通过**）。

**不可接受**：`__mods` 键集合或任一键的导出名集合变化；L3 金样任何字段变化；产物里出现 `^\s*import ` 或 `^\s*export ` 语句（一条 `grep` 就能当廉价门禁）。

**负例（补现有缺口）**：目前 `tests/` 下 grep 不到任何 `var __mods` / `not a function` / `__PALETTE_VERSION__` 的断言 —— v1.2.0 那条 ASI 修复**只靠注释守着**。推荐加一个负例：把 `var __mods = {};` 的分号去掉，断言 `vm` 加载抛 `TypeError`。这是唯一一处「已知事故 + 零测试」的组合，做起来 10 行。

## 7. 结论与推荐路径

1. **现状撑得住，但只撑一种风格**：只要源码保持「无分号、单引号、单行 import、`.mjs`、无 `as` 别名」，236 条语句 100% 命中，`UNHANDLED = 0`。
2. **它撑不住任何默认格式化**：4 条 `$` 锚定正则对分号零容忍，而分号是 prettier 与 tsc 的默认输出。这是**当前就存在**的脆弱点，不必等迁 TS —— 谁对 `src/engine/*.mjs` 跑一次格式化，`npm run build` 就 exit 0 地写出坏 bundle，全靠 `npm test` 的 vm 加载兜住。
3. **最近可行路径（不改 bundler 语义）**：
   - **B 先行**：放宽 `:128/:129/:130/:272` 四处 + `\.mjs → \.m?js`，6 行 diff + 1 个 fixture 测试。零新增依赖、确定性高、不触碰生成逻辑。
   - **C-lite 随后**（仅在真正决定迁 TS 时）：tsc emit 到 `dist/`，`module/moduleResolution: NodeNext`、`target: ES2022`、禁止 `importHelpers`（否则 `tslib`）、禁止 minify、不开 inline source map；构建器只换两个目录常量 + `:391` 一格扩展名；引擎/宿主/7 个测试/`generate-assets.mjs` 一起改指向。
4. **事实上最省风险的是 B**：它单独成立、与是否迁 TS 解耦、失败面最小（只改「是否识别」）、且正好覆盖 v1.2.0 的同一类根因（构建期静默产坏 bundle）。C 在 B 之前做没有意义——不先放宽正则，C 读进来的 emit 产物每行都破。
5. **明确不推荐**：A（多一层文本变换，与事故教训反向）、D（违反 `DESIGN.md` §7，且是架构级重写 + 要重写 5 处 bundle 文本断言）。
6. **真迁 TS 的两条硬提醒**：
   - `.ts` 在根 `package.json` 的 `"type": "module"` 下 emit `.js`，源码说明符必须写 `'./x.js'`；正则必须接受 `.js`，否则 34 条全灭。想保住 `.mjs` 就得把源命名成 `.mts`（生态少见，但零正则改动）。
   - `src/engine/index.mjs:43` 那条 `export { … }` 是 17 个名字的唯一出口，tsc 会给它补分号，`runtime/client.mjs:4` 会因此拿不到东西——这是全仓迁移里**单点收益最高、也最容易被忽略**的一行。

## 8. 证据缺口

1. **未实测 tsc / esbuild**（不能安装）：以下未验证，只用本仓 `node_modules/*/dist` 的真实 emit 样本外推——tsc 对 import attributes 的引号与空格是否规范化、是否会把多行 import 折叠成一行、`resolveJsonModule` 是否把 `.json` 复制进 `outDir`、`verbatimModuleSyntax` 下的 emit 形态、esbuild 逐文件 transform 是否保留原引号。

3. **L1/L2/L3 门禁是本文提出的方案，尚未实现**；`MODULE_ORDER` 的「顺序 = 依赖顺序」至今无自动校验。
