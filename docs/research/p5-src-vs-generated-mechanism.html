palette.src.yaml 与 palette.yaml：机制说明

一句话

palette.src.yaml 是手写源，palette.yaml 是生成物；人只改源，机器跑生成器产出后者。

两个文件的角色

文件谁写内容能手改吗
palette/palette.src.yaml 人 / AI 手写能力 28 条（颜色语义、字体、背景、玻璃、图标等）+ 4 类控件模板 + api / palette_version 头 能，且只改这里
palette/palette.yaml 生成器 能力菜单 capabilities 331 条（手写 28 + 研究表 master 236 + P4 52 + P2 20，合并去重后）+ 直绑定 direct_bindings 425 条（425 个公开 token 一一对应） 不能；改了会被门禁判为漂移

生成链

palette/palette.src.yaml（手写能力）
＋ docs/research/capability-master.json（P1–P4 已逐条讨论的 236 条效果能力）
＋ color-ability-map.json / noncolor-surface-map.json / private-surface-map.json（P1/P4/P2 逐条表）
＋ palette/tokens.yaml（425 个宿主 token 事实：状态、值类型、消费、声明）
↓ scripts/research/gen_palette_v5.py（可重跑，同输入同输出）
palette/palette.yaml（331 条能力 + 425 条直绑定）
↓ scripts/research/palette-check.py（门禁：id 文法/域、token 存在与状态、425 全覆盖、直绑定与 token 一致、计数、版本）
结果：0 错 0 警；P1–P4 每一行 → YAML 落点见 v3-p1p4-to-yaml-crosswalk.html

为什么要拆

理由说明
防漂移425 条直绑定是机械重复：每个 token 一条、字段固定。手写必然和 tokens.yaml 对不上，生成才可能真正「425 全覆盖」。
可审计331 条能力里 236 条来自已讨论、已逐条过目的 P1–P4 表。生成链让「讨论表 → 能力集」可一行一行核对（crosswalk），而不是人手抄一遍。
可扩展宿主升级加新 token → 重跑扫描器更新 tokens.yaml → 重跑生成器，直绑定自动多一条；不用人补 425 行中的任何一行。

这是不是最新敲定的最终机制

是。P5 定稿（提交 be5d97e，palette/SPEC.md v1.12）定的就是这个：手写源 + 生成物 + 门禁，三件套。

它的前身是「palette.yaml 手写」：P5 之前 palette.yaml 是手写的 28 条；P1–P4 讨论出 331 条能力与 425 个 token 后，再手写已不现实，所以拆成源与产物。你之前说的「多个 yaml 最终构造出 palette yaml」在这里的落地就是：手写源 + 各研究表 + token 事实表 → 合成为 palette.yaml。
