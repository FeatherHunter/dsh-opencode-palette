0. 今天已经定下的格式结论（有原话，不再重问）

#结论含义
1theme.yaml 只有 5 个键 api / meta / variables / capabilities / extensions；资源放 assets/，不是键。
2不要 _index.yaml 源片各自带 module 头，构建扫目录合成 palette.yaml；计数由构建写入合成文件头部。
3完全不支持 raw_tokens 能力覆盖不了 token 之外的技术，且自由文本难校验、维护不值。
4425 全覆盖靠「直绑定条目」 语义能力 + 构建期自动生成的直绑定条目，CI 保证 425 个 token 每条都有条目、都有值类型。
5能力 → 底层实现技术 token 只是五条实现路线之一；能力条目记录的是「靠哪条技术、绑哪个落点」。
6先谈技术上限，再谈能力条目 本文件就是第 1 组（公开 token）；后续依次私有契约面 / DOM / 资源 / 字体 / 外壳。

4. 两种条目的样子（这就是 A 方案的两层）

语义条目（人用）

- id: sidebar.panel.background
  label: 侧栏背景
  value_type: paint        # 颜色 / 渐变 / 图片
  tier: stable
  realization:
    use: token
    name: --dsw-specific-sidebar-fill
按界面区域/角色命名；编辑器里显示中文名；值有类型校验。

直绑定条目（全量兜底）

- id: token.static-blue-450
  label: "蓝 450（--dsw-static-blue-450）"
  value_type: color
  tier: experimental       # 默认收起
  realization:
    use: token
    name: --dsw-static-blue-450
构建期从 tokens 表自动生成；保证 425 条每条可点到；死名标 dead 并注明「宿主无消费方」。

待你裁定：颜色 222 组按哪种形态做？

  • A（推荐）：两层 —— 语义条目约 100–120 条（tier 稳定）+ 直绑定 222 条（含死名，tier 实验、默认收起）。人用语义，AI 用全量。
  • B：只做语义条目，直绑定后置（一部分 token 暂不可达）。
  • C：只做直绑定 222 条（全量但人的可用性最差）。
回复「A」「B」或「C」即可。定了之后我把颜色组的语义条目清单逐项列出来给你过，再进排印组。

5. 下一步（按顺序，一组一张表）

  1. 公开 token 425（本文件）：颜色 → 排印 → 圆角/形状 → 材质 → 渐变 → 交互/外壳
