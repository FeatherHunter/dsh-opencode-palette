P1 / P2 / P3 设计的核心思路

从第一性原理出发 · 2026-10-24 · 对应文件：P1 颜色 222 / P2 私有契约面 / P3 DOM 层 / 能力主表

0. 第一性问题：屏幕上的像素由什么决定？

主题系统要回答的唯一问题：「用户想改的那个视觉效果，最终由什么被决定？」

浏览器把一个像素画出来，只有四类输入：

  1. DOM 结构：有哪些节点、什么属性、什么层级。
  2. CSSOM：样式表规则、内联声明、自定义属性（token）的值。
  3. 媒体资源：图片、视频、音频解码出的像素。
  4. 字体：字形轮廓、度量、栅格化。

没有第五类输入。Canvas/WebGL/shader 最终也落到 DOM（canvas 节点）+ 代码，不是新的像素输入源；所以穷举这四类，就是穷举「能改什么」。

1. 由输入推出 5 条写通道（完备性）

① DOM→C3 增删改节点 ② CSSOM→C1 写自定义属性值（token）+C2 写规则/内联 ③ 媒体→C4 资源文件 ④ 字体→C5 @font-face

关键推理：CSSOM 有两个独立写入口 —— 改「自定义属性的值」（C1，官方 API 就是给这个用的）和改「规则表/内联声明」（C2，任意选择器+任意属性）。它们不是同一件事：C1 只能改宿主已经消费的名字，C2 能凭空新增效果（如毛玻璃、动效、噪点）。

所以 5 = 4 类输入 + 1 次 CSSOM 拆分，不多不少。这是「我们不可能漏掉一种改法」的证明骨架。

2. 通道里「谁可写」由宿主事实决定，不由偏好决定

通道「可写对象」是什么谁决定边界对应设计
C1 token宿主声明并消费的变量名宿主 CSS：425 个主题命名空间 + 运行时 573 个变量P1（颜色 222）
C2 规则选择器能命中的元素 + 合法声明的属性宿主 DOM 的锚点（data-slot / role / 全局类）与 CSS 白名单P2 部分 + P3 部分
C3 DOM页面内节点（增删改）React 重渲染的存活率；宿主私有类名不可依赖P3
C4 媒体主题包内资源体积/格式限制 + 插入位置P3 背景媒体行
C5 字体@font-face 与字族unicode-range、字体文件可加载性P4 排印

第一性要求：先列宿主事实（名字/锚点/存活率），再谈能力。能力不是「我们想做」，而是「宿主允许我们写 + 用户能看见」的交集。

3. P1 的核心：颜色 = 222 个可寻址的「语义输入」

为什么从颜色开始：颜色是 CSSOM 里被消费最广、改一条 token 就能全站生效的输入；它也是用户第一眼看到的东西。

三条设计铁律：

  1. 集合封闭：颜色轴 = 222 名（alias 107 + specific 11 + shiki 11 + static 77 + focus 1 + menu 1 + shadow 4 + elevation 5 + gradient 3 + linear 2），222 条一条不少；状态分 live 184 / gated 5 / dead 38，dead 也登记（用户要「全量收录」）。
  2. 一个 token 一个语义：222 个建议语义能力 + 222 个直绑定兜底（token.<名>），不合并（用户裁定 m03131）。合并会省事，但会丢精度。
  3. 每条回答五个问题：是什么 / 能改什么 / 值类型（是否成对）/ 靠哪条实现技术生效 / 失败如何诊断。所以表里有 消费来源、成对、探针、tier/暴露、实现技术链。
P1 暴露的一个反直觉事实：「名字存在」不等于「改了就生效」。222 里 38 个是死名（没有消费方），5 个是 gated（宿主在元素级重声明，body 写入会被盖，必须 token+规则双写）。所以能力表必须带「状态」与「实现技术」，否则编辑器会把死名当可用项。

4. P2 的核心：私有面 = 问「这个值归谁拥有」

P2 覆盖四类灰色地带：--dsl-* 20 条、--terminal-cursor* 4 条、inline 28 种 / 74 点、硬编码色 381 行（含 13 个 fallback）。

第一性判据：看这个变量的值上游是谁——

  • 值里引用 var(--dsw-*) 的：能力指向上游 token，不新增重复能力（否则同一效果两个入口，违反「一个语义一个条目」）。
  • 纯本地声明、无上游的：能力落在规则层（选择器命中该元素），值类型是 length/keyword。
  • 宿主用 JS 逐元素 inline 写的（终端光标）：只能运行时重写 + MutationObserver 幂等重放，并接受「重渲染会再写一次」的事实。
  • 硬编码色：var(--token, #hex) 的 fallback 能救（设 token 即覆盖）；独立字面量救不了，诚实标「不在用户能力范围」，不假装能改。

5. P3 的核心：DOM 层按「存活率」分档，而不是按「想要程度」

档做什么存活率事实设计
stable · 装饰性插背景层、换图标、插官方 slot 入口卸载 4/4；重渲染靠 MutationObserver 幂等重放正式开放，必须写 teardown + guard
experimental · 结构性隐藏/移动/重排控件、插 HTML 片段重渲染仅 1/4 存活；可能破坏键盘可达性默认关闭 + 强提示 + 一键恢复
不做原生标题栏内部、跨 Shadow Root、跨文档、音频/BGM、canvas shader物理或契约不可能写明「做不到」与原因
锚点的第一性：规则/DOM 能命中谁，是宿主 DOM 的客观事实，不是我们的猜测。所以 P3 的锚点只认「宿主测试里反查到的 data-slot 真实取值」（19 个），配合 role/全局类；哈希类名只能按后缀兜底，不能写死；写死的猜测锚点一律删掉。

6. 三张表为什么必须能被同一套验收检验

能力条目的「可信」不是看起来能，而是同时过四道客观判据（U20 的实现口径）：

  1. 重渲染存活：宿主重渲染后效果还在（DOM 层靠 observer 重放）。
  2. 主题切换存活：D→E 失败时保持 D（事务性切换，dry-run 预编译）。
  3. 卸载全还原：每个 write 有稳定 id + teardown，切主题差集清理。
  4. 上游升级不炸：锚点/名字走 probe，unknown → 降级或跳过 + 诊断，不抛错。

再加第五道底线：可探测（每条能力带 probe：token_live / selector_exists），没有探针的能力不算能力。

7. 为什么要有能力主表（P0-2 的修复）

P1/P2/P3 是「按底层技术切」的三份清单，天然会出现同一效果跨技术重复：焦点环既是 token 又是规则；滚动条既是 4 个 token 又是伪元素规则；菜单材质面既是 token 又是 backdrop-filter。

所以加一层能力主表：以「用户看到的效果」为唯一身份（capability_id），下面并列多条实现技术链（token→rule→runtime）。规则是：

  • 主表每条能力 = 一个效果；实现技术可以多条，但身份唯一。
  • P1 的 222 条直绑定不删，作为 fallback 兜底（保证 222 全可达）。
  • P2/P3 新增的能力都必须能回答「为什么不是已有能力的重复」。

8. 全套推理链（一句话版）

像素由 4 类输入决定 → CSSOM 拆成 2 个写口 → 5 条通道穷尽 → 每条通道的「可写对象」由宿主事实界定 → 把事实逐条变成可寻址的能力（P1 颜色 222 / P2 私有面 / P3 DOM）→ 同一效果合并进主表、直绑定兜底兜住全量 → 每条能力过四道验收 + 探针 → 24 条需求逐条溯源 → 集合算术保证不漏（425 = 222 + 203；573 = 425 + 148）→ 做不到的写进「明确不做」并给原因。

9. 这套思路的三个可检验推论

推论检验方式当前结果
不可能漏掉一种改法4 类输入 × 写口穷举；任何新效果必须能归到 C1–C5生态 20 款插件 100% 落在 5 通道内；唯一通道外现象是「改已构建前端产物」，JS 插件做不到
不漏一个 token集合算术 + 生成器扫描（不手抄）425 = 222 颜色 + 203 非颜色；222 = 184 live + 5 gated + 38 dead；均有机器生成清单
每个能力可验证四道验收 + probe + 构建期 id 文法校验222 id 与 222 直绑定 id 0 违规 0 重名；checker 0 错 0 警

一句话总结：P1 解决「颜色输入有多少个可寻址单位」；P2 解决「灰色地带的值该归谁管」；P3 解决「DOM 层按存活率能开放到什么程度」；主表解决「同一效果不要重复登记」；覆盖声明 + 集合算术解决「不许漏」；四道验收 + 探针解决「不许假」；明确不做清单解决「不许装」。
