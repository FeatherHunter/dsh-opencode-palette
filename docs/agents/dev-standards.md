# 开发规范（维护者 2026-10-24 指令，逐字）

> 来源：维护者本会话指令（2026-10-24 m04545）。后续所有开发、推进问题都按本规范决策。

1. 如果开发时需要修改 js 的代码，则需要重构为 TS 代码。
2. 需要符合纯 TS 项目的优秀和权威的架构设计、代码细节。
3. 需要符合优秀的数据结构。
4. 需要符合优秀的算法。
5. 需要符合优秀的设计模式。
6. 需要符合高级架构师思维。
7. 从第一性原理出发。
8. 过程中要有对抗式审查。
9. 目录结构、目录名、文件名等需要具备自解释的能力，架构师层面拆分好目录。
10. 不要过度发散思维。
11. 充分封装和解耦、组件具备可复用性。

## 在本仓的落地口径

| 规则 | 本仓落地 |
|---|---|
| 1 JS → TS | 源码与测试一律 `.ts`（Node 原生类型剥离直跑，见 ADR 0003）；`client.js` 只是构建产物（ADR 0004），不手改；发现遗留 `.js` 源码先迁移再改 |
| 2 纯 TS 架构 | `strict` 类型；领域层（`src/engine/`）不依赖 DOM/宿主；边界用显式类型 + 结果对象，不用 `any` 逃逸 |
| 3 数据结构 | 先定形状再写逻辑：能力/绑定/主题 plan 都用显式 interface + 不可变数据结构；避免并行数组与隐式约定 |
| 4 算法 | 编译/校验/合并类逻辑给复杂度说明；用集合/映射做归属与去重，不用 O(n²) 扫描 |
| 5 设计模式 | 策略链（token→规则→DOM→资源）、模板方法（生成器）、适配器（宿主差异）、不可变快照（切换事务） |
| 6 架构师思维 | 先写接口与不变量，再写实现；跨模块契约进 SPEC；破坏性变更走版本与迁移 |
| 7 第一性原理 | 先问「像素/行为由什么决定」再选技术；结论必须能从宿主事实推出 |
| 8 对抗式审查 | 每个里程碑：独立只读复核（P0/P1/P2 + 文件:行号）+ 变异测试（改错必须让门禁变红） |
| 9 自解释命名 | 目录按职责分层（`engine/` 领域、`runtime/` 宿主集成、`ui/` 组件、`palette/` 规格、`scripts/research/` 研究工具）；文件名说清「是什么」而不是「第几步」 |
| 10 不过度发散 | 一次只推进一个里程碑；新增抽象必须有当期需求支撑；研究结论落盘后不再重复讨论 |
| 11 封装/解耦/复用 | 能力与绑定只通过登记表交互；生成器与校验器分离；UI 组件不直接读宿主 token 名 |
